## Running tests

Vitest 5 with two projects in `vitest.config.mts` (the package stays CommonJS; the config uses `import.meta.dirname`): `unit` (`tests/unit`, no database, no network) and `integration` (`tests/integration`, file-parallel, real PostgreSQL on the Compose `db` service, needs `npm run db:up`). Integration runs N workers, N = `integrationWorkers()` exported by `vitest.config.mts` (`INTEGRATION_WORKERS` from the process environment, not `.env`, else `min(8, cpus - 1)`; an invalid value throws), in `sequence.groupOrder: 1`, so Vitest numbers them `VITEST_POOL_ID` 1..N. `tests/support/global-setup.ts` drops every database `isIntegrationDatabase` names (`${DB_NAME}_tpl_test`, `${DB_NAME}_w<n>_test`, the old `${DB_NAME}_test`), migrates `${DB_NAME}_tpl_test` with `runMigrations` from `src/db/migrate.ts`, clones it one at a time to `${DB_NAME}_w<n>_test` for n = 1..`project.config.maxWorkers`, and `provide`s N as `integrationWorkers`; the clones stay after the run. After `runMigrations`, the setup copies `categories` and `vehicles` into schema `test_fixture` (`SNAPSHOT_SQL` in `tests/support/db.ts`); clones inherit it, and `public` never shows it. `tests/integration/reset-database.test.ts` pins the reset's post-state against the template's own state. `tests/support/test-database-env.ts` points `DATABASE_URL` at the worker's own clone and throws a named error for a missing or out-of-range pool id. Naming helpers live in `tests/support/env.ts` (unit tests: `test-database-names.test.ts`). Integration files call `resetDatabase()` (`tests/support/db.ts`) in `beforeEach` and `closeDb()` in `afterAll`. Playwright in `tests/e2e`, chromium only, against its own Compose project `los-tres-e2e` (compose.yaml plus tests/e2e/compose.e2e.yaml), built, started and removed by global setup and teardown at `http://127.0.0.1:${E2E_APP_PORT:-3020}` (four consecutive ports: the app, then `app-no-db`, `app-flag-off`, `app-flag-on`); no webServer; needs only Docker and `.env`. Commands: `npm run test:unit`, `test:integration`, `test` (both), `npm run check` (lint, typecheck, db:up, test: all of Vitest, no image build, no Playwright, budget 90 s; what a build lane verifies with, 0006 rule 8), `test:e2e`, `test:e2e:install`, and `npm run gate` = `npm run check`, then `test:e2e` (it does not run `stack:up`). Env comes from `.env` via `process.loadEnvFile`. Helpers in `tests/support`, fixtures in `tests/fixtures`.

A third config, `vitest.timing.config.mts`, has one project `timing` over `tests/timing/**/*.timing.test.ts` (`maxWorkers: 1`, `fileParallelism: false`, the integration `globalSetup` and `setupFiles`, the alias imported from `vitest.config.mts` as `./vitest.config.mjs`). `npm run test:timing` runs it; no gate step does. `tests/unit/gate-determinism.test.ts` pins that over `vitest.config.mts` includes, the `package.json` scripts (walked through calls, `pre`/`post` hooks and install steps from the gate entries) and the text of `.github/workflows/*.yml`: `gate.yml` (four jobs: `static`, `integration`, `e2e` and the aggregator `gate`, which needs the three, runs `always()` and fails unless each result is `success`; read access only, no job sets its own; the three jobs' steps together are the local gate's steps with `test` as `test:unit` plus `test:integration`, and no line runs `npm run gate` or `npm run check`; the `e2e` job reads the locked `@playwright/test` version from `package-lock.json`, caches `~/.cache/ms-playwright` on `playwright-${{ runner.os }}-chromium-<version>` with no `restore-keys`, uploads `playwright-test-results-${{ matrix.attempt || 'gate' }}-${{ github.run_attempt }}` and has no `docker compose` line), and for `gate-repeat.yml` each of the three copy jobs (`copy-static`, `copy-integration`, `copy-e2e`, one per working job, `PAIRS` in the test) against its `gate.yml` job (steps equal, the checkout `ref` the one allowed difference, same settings and timeout, named `repeat <n> <part>`), its trigger (`workflow_dispatch` only), no job named `gate`, a swallowed failure only in its `timing` job (plus one exact line in `plan`), `plan`'s `ref` output set only to empty or the checked merge commit and taken by every other job's checkout, `plan`'s `runs` and `pr` checks as whole-value bash matches (never `grep`) that end in an error and `exit 1`, top-level `permissions` of exactly `contents: read` with no secret, and the `strategy` of each copy job (`fail-fast: false`, matrix from `plan`, no `max-parallel`). It reads text with no YAML parser, so an expression-built name, a YAML anchor, a reusable-workflow job or a script file a step calls is not seen: review covers them. It also pins the retry rule and the clock directive form (§ Shared scaffolding and gotchas, "Clock in tests"). It also pins `npm run check` (0006 rule 8): `steps()` expands it to lint, typecheck, db:up, test in order; nothing reached from it, hooks included, is stack:up, an e2e run, build, dev or text with `playwright` or `--build`; `scripts.test` is `vitest run`; gate expands to check's steps plus `test:e2e`, and nothing reaches `stack:up`; check and gate are each bare npm calls joined by `&&`. It also pins the e2e stack (#363, describe "the e2e run owns its stack: one project, set in the config"): one global setup and one global teardown named in the config; the project name assigned once in `playwright.config.ts`, not the development project, with the compose files and image following it; only `e2e-stack.ts` reads `COMPOSE_PROJECT_NAME` or spawns `docker`; only `global-setup.ts` and `global-teardown.ts` match its lifecycle detector (quoted `run`, `rm`, `create`, `start`, `stop`, `kill`, `restart`, `up`, `down`, `build`, `pause` or `unpause` in an argument list, or `--network`); `SERIAL_SPECS` is a literal list of existing specs that holds every spec that writes the main e2e database: a bare `psql(` call (not the `.psql(` method of a variant), `createAdminWithCommand(`, or `verb(` whose first argument is not the literal `'app-no-db'`, `'app-flag-off'` or `'app-flag-on'` (pass the literal to `verb()` in the spec itself, not through a service parameter); the config has exactly the projects `chromium` and `serial` (`dependencies: ['chromium']`, `workers: 1`) and no other `workers:` key. Its global setup drops every integration database and clones only `_w1_test`; the next integration run drops and rebuilds all of them, so no manual step is needed, but it must not run beside another Vitest run.

For a scripted edit or a scratch script use `python`, or `node -e`; `python3` may be the Microsoft Store stub on Windows (it exits 49) while `python` is the real interpreter.

A config that must reuse `vitest.config.mts` imports it as `./vitest.config.mjs`: TypeScript maps it to the `.mts` file with no `allowImportingTsExtensions`, and Vite's config bundler resolves it. `vitest.config.mts` exports `alias` for that reason.

`CLAUDE.md` § Commands is the authority for the command list.

Integration run time no longer depends on the previous run: `resetDatabase` deletes rows instead of truncating, so it leaves no new relation files and the next run's first `drop database` forces a checkpoint of about 3 s (measured 2.8 s after a full run, 87 s with the TRUNCATE reset). `pg_stat_checkpointer.sync_time` shows it. A run right after another takes the same 40 to 50 s as one after idle.

No Playwright test is tagged and no project filters by grep: CI runs the gate's steps in three jobs (`static`, `integration`, `e2e`, plus the aggregator `gate`), the same steps and the same browser tests as the local gate. `tests/unit/gate-determinism.test.ts` (describe 'CI and the local gate run the same browser tests') fails on grep or grepInvert in the config, `@layout` in a spec, a `gate:ci` or `test:e2e:ci` script, or either name in a workflow's non-comment lines.

`collected-public`, `collected-start` and `entrypoint` are chromium specs: they run every verb in `app-no-db` and write only the variant databases through `app.psql(`. The only serial specs are `admin`, `admin-categories`, `admin-feeds`, `admin-products` and `catalogue-file-flow`.

`vitest.config.mts` and `playwright.config.ts` must not import from `tests/`: tsconfig includes them, `next build` typechecks them in the image, and `.dockerignore` removes `tests/`. Put shared logic behind `setupFiles` or `globalSetup` instead (Playwright's takes a string path).

E2E data comes from Playwright `globalSetup` (`tests/e2e/global-setup.ts`): it removes any leftover `los-tres-e2e` project, builds the app image, starts the stack on a fresh volume, runs the `import-feeds` verb on `app`, `app-flag-off` and `app-flag-on` (each has its own database), creates the one admin, and throws a named message on `feeds=0` (quoted in `CLAUDE.md` § Commands). `global-teardown.ts` removes the project with its volume on every exit path. The e2e write rule is in § What must always be covered.

An e2e that hides or changes public data runs in project `serial`, after every `chromium` spec has finished, on the one e2e `app`: nothing reads the demo rows beside the write. It must leave nothing changed that a later spec reads: no hidden demo item (`admin-products.spec.ts` `restoreHidden()` before and after) and no changed demo mapping.

An e2e must leave no feed or shop approved that it created (the next `import-feeds`, global setup's included, reads every approved feed). `entrypoint.spec.ts` runs only in `app-no-db` and asserts no totals; no browser test covers the collected-file feed in the admin now (its writers and actions are `tests/integration/collected-feed-admin.test.ts`). `admin-categories.spec.ts` keeps its fixed shop and feeds unapproved and proves the public side of guardrail 1 that way (a mapping on an unapproved feed publishes nothing); removal of an approved product is proved off the public readers in integration (importer-removal.test.ts, hide-public-sweep.test.ts); the one e2e removal test lives in catalogue-file-flow.spec.ts, which owns an approved feed, unapproves it in the spec, and cleans its rows (`cleanRows()` in `beforeAll` and `afterAll`, which deletes its replacement product).

A spec in project `serial` also runs its dependency `chromium` in full unless told not to: `npx playwright test tests/e2e/admin-feeds.spec.ts` ran 49 tests (every chromium spec, then J9), 53.6 s, not 1. Run one alone with `npx playwright test <file> --project serial --no-deps`.

`legal.spec.ts` branches on the host `.env`: all four required `OWNER_*` values non-blank means 200 and values asserted as booleans (never printed), otherwise 500 and no brace in the visible text. To exercise the 200 branch without touching `.env`, export fake `OWNER_*` in the shell and run playwright with the same exports: the e2e stack is built and started by that run with the shell's values (Compose gives the shell precedence over `.env`) and removed after it, so there is nothing to restore and the dev stack is not touched.

Integration workers get fixed `AUTH_SECRET` and `SITE_URL` (`http://127.0.0.1:3000`) from `tests/support/test-database-env.ts`, so admin tests run without them in `.env`. Server components and actions are called directly with `next/headers` mocked: `vi.mock('next/headers', async () => (await import('../support/next-request')).nextHeadersModule)`; `startAdminRequest({cookie, origin})` sets the request, `nextRequest.cookieWrites` records every cookie the code under test would send, `redirectOf(fn)` returns the `NEXT_REDIRECT` target.

Actions in `src/app/admin` are tested by importing them with `next/headers` mocked and `next/cache` mocked as `{ revalidatePath: vi.fn() }`; without the second mock `revalidatePath` throws outside a Next request.

The global setup creates one admin, `E2E_ADMIN` (`tests/support/e2e-stack.ts`); every admin spec signs in with `signInAsAdmin(page)`; only the create-admin test in `admin.spec.ts` calls `createAdminWithCommand`, on its own email; never create `E2E_ADMIN`'s email again (it ends the sessions of every other spec). The e2e app's `SITE_URL` is set by `compose.e2e.yaml`, so an old `.env` without `SITE_URL` still runs the admin specs; `AUTH_SECRET` still comes from `.env`.

E2E canonical, robots and sitemap checks read the `baseURL` origin, which equals the e2e app's `SITE_URL` (`http://127.0.0.1:${E2E_APP_PORT}`, set by `compose.e2e.yaml`, not the `SITE_URL` of `.env`); demo data makes the indexable side e2e-unreachable, so it lives in `integration/indexable.test.ts`.

The default e2e host port is 3020 (`E2E_APP_PORT`, with the next three ports used by the variant apps) and may be taken, so never write a literal base URL: specs use the `baseURL` and `request` fixtures (a context made from `browser` gets no config base URL: `browser.newContext({ baseURL: origin('app') })`), and only `playwright.config.ts` computes it from `.env`; `origin(service)` of `tests/support/e2e-stack.ts` gives a variant's origin.

Home e2e selects `home-panel`, `home-search[-input|-button|-notice]`, `home-all-link`, `home-all-count`, `category-tiles`, `category-tile[-link|-name|-count]` and `site-header-link`; the home count text is `icuPlural(messages.Home.productCount, n)`. Demo state is four tiles (the empty fuel category has none, in position order); the five-tile and one-tile states are unit renders (S11.3).

`search-privacy.spec.ts` runs in project `chromium` and reads the e2e stack through `tests/support/e2e-stack.ts`: app logs by `serviceLogs`, the failing server is the `app-no-db` service (a database address that cannot be reached), and the `pg_dump --data-only` goes through `execIn('db', ...)`. It starts no container.

Privacy assertions are contains/absent, never counts: the failing search logs its fixed code three times per request.

`playwright.config.ts` keeps trace and screenshot on failure; `gate.yml` and `gate-repeat.yml` upload `test-results/` for 7 days from an identical `if: failure()` step (#361).

No spec starts, stops or removes a container: the stack is up before the first test. A spec that writes the main e2e database (the rule in the `SERIAL_SPECS` pin above) is in `SERIAL_SPECS` of `playwright.config.ts` and runs in project `serial` (one worker, after `chromium`); `gate-determinism.test.ts` pins the list, the project blocks and that only `global-setup.ts` and `global-teardown.ts` match its lifecycle detector. The reason is #361 and 0006 rule 6: a container's start or stop changes a network interface and Chromium cancels the page loads waiting on a socket (`net::ERR_NETWORK_CHANGED`). No retry, reload, sleep or longer timeout.

A `node server.js` exec into `app-no-db` must pass `PORT` (collected-start uses 3999): the service's own server holds 3000 and the framework binds the port before its start hook runs, so the refusal never shows (EADDRINUSE, exit 1).

Each e2e run builds the app image itself (cached when nothing changed), so a `src` edit or a CSS mutation an e2e checks takes effect on the next `npm run test:e2e` with no `npm run stack:up`; `stack:up` starts the dev stack and no e2e reads it.

A raw-HTML "value never appears" assertion must strip `<script>` blocks first: Next puts the request URL (query included) in the inline flight payload, so the typed `q` is in the raw response even though app code never renders it.

Listing e2e select only by the `data-testid` values of the design contract; the category name is read by `getByRole` heading level 1. Category pages are server pages: parse `request().get` HTML with `openRawHtml` for JS-off checks.

Category listing (S11.4): integration tests call `getPublicCategoryPage(slug, page, brand, sort)` and set `products.brandNormalised` and `partNumber` themselves (`insertListedProduct` sets neither; the local helper `listBranded` in `category-page.test.ts` does it). Canonical on `?marca=`/`?orden=` is proven by importing `generateMetadata` from `src/app/(public)/categoria/[slug]/page` in an integration test with `vi.mock('next-intl/server', () => ({ getTranslations: async () => (key) => key }))`; `SITE_URL` comes from `test-database-env.ts`.

A pin that sweeps every internal anchor on a product page must take the vehicle list out and assert its tiles as their own vehicle (category path, `coche` once, the only parameter): the tiles are the one link whose `coche` is not the selected car (`expectCarried` and the tile check of journey J7 in `car-links.spec.ts`).

`product.spec.ts` is an aria smoke and clicks nothing. The one browser click-through is journey J7 in `car-links.spec.ts` (the shop's request carries no `coche` in its Referer). The Referer click source is stored and proved in `tests/integration/go-counting.test.ts` (with `go-redirect.test.ts` and `go-privacy.test.ts`) and `tests/unit/click-source-page.test.ts`; that the shop anchors are plain (no target, noreferrer, referrerpolicy) is `tests/unit/product-components.test.ts`.

Product JSON-LD e2e reads the raw `request.get` HTML with a regex over script tags (expect one match) and `JSON.parse`, then `openRawHtml` for the selector and the visible-price comparison; selector `script[type="application/ld+json"][data-testid="product-jsonld"]`.

The nested 404 (missing product, missing category, page or brand past the last) is a full server-rendered page: `src/proxy.ts` rewrites it to the root not-found. Assert the served body with `expectServerRenderedNotFound(html, siteName)` (`tests/support/page-checks.ts`), which strips `<script>` first; a `toContain` on the raw body passes on the flight payload and proves nothing. A Tab walk right after `goto` can lose the first Tab to hydration: wait for the button visible and `networkidle` before pressing.

A page-title or generateMetadata pin must run against the Compose image: Next dev and the production build differ on whether a not-found boundary's metadata replaces the page's, so a dev-server curl is not proof.

Expected site name and copy come from `SITE_NAME` in `.env` and `messages/es-ES.json`, never a literal. Raw server HTML is parsed by `page.setContent` in a context with `javaScriptEnabled: false`, not by an HTML parser dependency.

## What must always be covered

These are the guardrails' tests. A slice that touches a seam owes the
matching test, and it should be one that would fail if the rule broke:

- **(1)** No public read (search, category, product page, sitemap,
  `/go/<offer>`) returns an offer from an unapproved or disabled feed, a hidden
  product or offer, or a product waiting in the matching queue.
  - A removed offer (`offers.is_removed`) is on no public reader: `hide-public-sweep.test.ts` sets it with `setOfferRemoved` and asserts the same surfaces as a hidden offer; `seams.test.ts` fences the flag to `visibility.ts`, `src/db`, the seed and the importer.
  - A hidden product or offer is proved off every public reader by `tests/integration/hide-public-sweep.test.ts` through the real writer; its `view()` helper reads page, 404 rewrite, category, home tree, search, sitemap, `/go` and car filter in one call.
  - A product with `products.category_id` null is not public: assert it on the shared scope (`visibility.test.ts`), the product page, `/go` and the category page. `tests/unit/seams.test.ts` keeps the `isNotNull(products.categoryId)` condition in `src/server/visibility.ts` only.
- **(2)** The importer refuses a source that is not a registered feed.
- **(3)** An anonymous request cannot reach any admin route or server action.
  - Proven by `tests/integration/admin-routes.test.ts`: any page, layout or route handler under `src/app/admin` that answers anonymous with content fails, and every `'use server'` export in `src` must start with `requireAdminAction` plus `isAdminRefusal` except `signInAction` and `signOutAction`; a `'use server'` file outside `src/server/auth`, `src/app/admin` and `src/components/admin` fails.
  - `findUnguardedAdminRoutes` also calls the `generate*` exports of admin pages and layouts; entries look like `file#generateMetadata`; `admin/layout.tsx` is in `METADATA_ALLOWLIST` (static title, serves sign-in).
- **(4)** Feed prices parse to integer cents. Include a case where float
  parsing would round wrongly (for example `19.99`, `0.29`).
- **(5)** A `/go/<offer>` click row holds no IP, user agent or cookie, and the
  response sets no cookie.
  - Counting rules are proven in the integration project one rule at a time on an otherwise countable request.
  - The e2e cannot show a counted row because every e2e offer is a demo offer.
  - The privacy test spies on `console.*` and reads `row_to_json` of the click row.
  - Admin cookie rules: only `signInAction` writes a cookie (`nextRequest.cookieWrites` is empty for every refusal, guard call and expired cookie); `admin_sessions` `ip_address` and `user_agent` are null (`admin-storage.test.ts`); sentinel logs in `admin-logs.test.ts`; the public no-cookie e2e stays on public routes and `admin.spec.ts` asserts the one `admin.session_token` cookie.
- **Search (S5.4).** `seams.test.ts` pins that `search-page.ts` names no flag and has one `console.error`.
- **Matching (0008), slice B cut:** EAN attach, EAN with a different brand
  becomes its own product with reason `ean_brand_conflict` in `report.ownProducts`
  (since S7.1; not a reject), null brand on either side
  attaches, no EAN creates a product, invalid EAN rejected. Brand + part-number matching (S7.1) is covered by importer-brand-part-number.test.ts, matching-index.test.ts and the own-product describe.each in importer-matching.test.ts (AC map in the S7.1 run, 05-test.md); a conflict or ambiguity is an own product with a reason in report.ownProducts, never a reject; the queue is not built.
- **es-ES prices and seams.** Assertions on es-ES prices normalise U+00A0
  (`normaliseSpaces`, `tests/support/messages.ts`). `tests/unit/seams.test.ts`
  scans the source so the visibility flags, `fetch(`, `node:fs`, `@/db` in
  pages and `/ 100` stay out of places they do not belong.

- **Sitemap and robots seam.** `seams.test.ts` `isSitemapOrRobotsFile` covers metadata files, route handlers under `sitemap.xml/` and `sitemaps/`, and `src/server/catalogue/sitemap*.ts`, and asserts at least 5 files so it cannot go vacuous.

- **Fixture size.** A fixture-size change reaches literals outside `tests/fixtures/demo.ts` that a grep for the constant misses: the page-count and page-length asserts, seed `approvedFeeds`. After changing the demo size grep tests for `feeds=`, `toHaveLength(1|2)`, `pageCount`, `[1, 2]` and `ROOT, 2`.

- **Count text.** A count-text guard must not substring-match (`/0 producto/` matches "50 productos"): anchor with `(^|\D)`, and escape query strings correctly in a template-literal RegExp.

- **Demo notice.** Any e2e that reads the first paragraph of `main` on a demo product or category page must skip `p[role=note]`.

Never call a live affiliate network in a test. Import from local fixture feed
files.

Any integration test or helper that writes to the database calls `assertTestDatabase()` (`tests/support/db.ts`) first, so it only ever writes this worker's own `${DB_NAME}_w<VITEST_POOL_ID>_test`; it refuses the template, another worker's database and any process without `VITEST_POOL_ID` (a throwaway bench that calls a helper sets `VITEST_POOL_ID=1` and names its database `<db>_w1_test`). e2e writes only the e2e project's database (`psql`/`psqlScalar` of `e2e-stack.ts`, fresh per run); a serial spec ends with nothing it created approved, no hidden demo item and no changed demo mapping (admin-products `restoreHidden`). The dev database is never written by an e2e.

Every public response is asserted to have no `Set-Cookie`; a browser visit also asserts `context.cookies()` is empty and no request leaves the app origin. The one exception is the `/go` click-through, which asserts the browser's request to the shop's `.example` host (§ Shared scaffolding and gotchas).

## Shared scaffolding and gotchas

- e2e global setup fails when an `import-feeds` run reports `failed` above 0, `feeds=0` (the named no-feed message: `SEED_DEMO_DATA=true` is missing in `.env`) or fewer than 2 imported feeds. The e2e database is fresh each run, so no approved feed from the dev database can cause it.
- `styles.test.ts` reads three token blocks of `globals.css` by selector (`:root`, `:root[data-theme='dark'], [data-theme='dark']`, `:root:not([data-theme])` under `@media (prefers-color-scheme: dark)`); raw colours are allowed only in their bodies; `themeProblems(text, required)` and `contrastProblems(set, pairs)` are pure and tested on in-memory CSS.
- `gate-determinism`'s retry scan matches `retry:` in any text of a test file, a comment included: write `no retry`, never `no retry:`.
- In the unit project a `.module.css` class renders as `_<name>_<hash>`; a markup test finds a group by `<div class="_trailing_`. Unit tests are `.test.ts` only, so render with `createElement`.
- `THEME_SCRIPT` is tested by `runInNewContext` with stubs defined on both the sandbox and `window`; a source-text mutation of a src constant is a `_mut.test.ts` that `vi.mock`s the module with `importOriginal` and re-imports the real test.
- A scanning test over src is mutated in a scratch copy of src, tests, messages and configs with a `node_modules` junction (`mklink /J`), never in the repo.
- The head-script first-paint check is an `addInitScript` MutationObserver that records `data-theme` when body first exists; proven to tell a head script from a late setter.
- Header wrap rules (#398 CR-1, CR-2) are pinned as CSS text in `site-header.test.ts` (SearchForm `.header .input` basis, the 22rem to 24.37rem `.trailing:has(> .carInline)` rule, the search-page basis auto) plus the markup nesting in `theme.test.ts`; heights are measured by ux-review, never a test.
- `theme.test.ts` `run(world, facts)` takes a shared facts record so a second run of `THEME_SCRIPT` records into the same list; `freshFacts()` makes one.
- `tests/support/e2e-stack.ts` is the one docker caller of the e2e run. `compose.e2e.yaml` `extends.file` resolves against the repo root, not the override file. A `pg_dump` md5 is unstable (random `\restrict` line): drop lines matching `^.(un)?restrict ` and `^--` before hashing. Even filtered, the md5 moves with no row change: `setval` lines move whenever a row is inserted, the dev app's start-up seed included (ON CONFLICT DO NOTHING still advances the sequence), and COPY row order moves after any UPDATE. Compare counts and the md5 without restarting the dev app in between, and restore a sequence with `setval` after deleting test rows.
