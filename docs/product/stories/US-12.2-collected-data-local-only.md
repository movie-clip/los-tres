## Standing constraints

These bind this story and everything built from it.

- **This story builds a wall and puts nothing on the other side of it (guardrail 2, decision 0017).** It adds no scraping, no collector feature, no collector code and no dependency. Public use of collected data stays forbidden and needs a new owner decision and a new decision record; nothing here allows it, and no AC below may be read as a step towards it.
- **The flag only lifts the exclusion of marked rows; it lifts nothing else (guardrail 1).** Approval of the feed and the shop, hide, review, removal and the category rule apply to a marked row exactly as to any row, flag or no flag (AC 13).
- **Marked rows are never indexed, never in the sitemap and never counted as clicks, whatever the flag says.** The flag decides whether a marked row is *visible* on a local site; it never decides whether it is *indexable* (ACs 20 to 25).
- **Local only, and fail closed.** "Local" is shown by the app's own public origin setting, not by where it happens to run. Anything that does not show a local origin refuses the flag (OD-2).
- **Roles are enforced on the server (guardrail 3).** Every action this story adds or changes checks the role on the server (ACs 9, 10).
- **No real shop is named in this repository, no capture of a real page and no collected file is committed.** The repo and the board are public. Every file, fixture and test uses invented shops and products.
- **No phone width and no visual polish check for admin screens.** Function, copy and the guardrails are checked.

## Open decisions

All six are ruled by the owner on the recommendation (D-1 to D-6 of run `2026-11-23-s12-2-local-only`, approved as a whole by D-7), and the ACs are written under those rulings. The options are kept as drafted, with the ACs that would move had the owner ruled the other way, so the reasons stay on record.

1. **OD-1. How does the importer know a file is collected?** (ruled (a), D-1). Today it cannot: a hand-written file and a collected one are both a "catalogue file" feed with a bare file name (recon § Source model and marker seam). Options:
   - **(a) A collected file has its own source and its own folder (recommended).** The admin form gains a third source choice, "collected file", beside the https address and the catalogue file. Such a feed reads only from a second fixed, git-ignored folder, and the importer marks every row it imports from it. Reason: it is the only option where the *place* a file sits decides the marker, so a copy to the wrong folder cannot make a collected file look hand-written *and* import; the two folders refuse each other's feeds (ACs 2, 3). The folder is then also what the ignore files and the compose mount name (ACs 40, 41). Cost: one more source on the S3.7 form, so the UX lane runs (admin only), and a second mount.
   - (b) The file name carries it (a prefix or a suffix) and the importer marks by name. Not recommended: a missing prefix fails open; one typo publishes collected rows as hand-written ones.
   - (c) The collector writes the marker into the file, and the importer marks and a hand-written feed refuses such a file. Not recommended now: it needs a change in the collector's own repository (S12.1, out of this story) and trusts the file's own claim; it is a good later hardening on top of (a), not a replacement for it.

   Under (a) no feed exists today with the marker, and the guide (ACs 48, 49) tells the owner that a collected file is placed only in the second folder and registered with the collected source. A file the owner put in `catalogue-files/` before this story ships cannot be detected afterwards by anything in the app (risk in Notes for the human). Moves with the ruling: ACs 1 to 8, 40, 41, 48 and the frontend ticket (under (b) or (c) no form changes, the UX pass shrinks to nothing and T-12.2.4 is dropped).
2. **OD-2. What is a "public https `SITE_URL`"?** (ruled (a), D-2). Nothing in the repo defines it; `.env.example` and `CLAUDE.md` § Search engines say only that `SITE_URL` must be the public https origin before a deploy (recon § Gaps). Options: **(a) the flag is allowed only when `SITE_URL` is an origin on the loopback interface (`localhost`, the `127.0.0.0/8` range or `::1`, either scheme); every other value refuses: a public https origin, a public http origin, a private-network address, an unparsable value, and an unset one (recommended).** Reason: the decision's intent is "never against a site that is public"; the stack's own default is `http://127.0.0.1:<port>`; and an allow-list fails closed, where a block-list of "https" would let `http://example.test` through. The cost is that a private LAN address with the flag, which the owner might use from a phone, is refused until he decides otherwise. (b) Refuse only when the origin is https and not loopback, the decision's words read literally; an http public origin, a LAN host and an unset value start. Not recommended: it fails open on exactly the misconfigurations a hurried deploy produces. Moves with the ruling: ACs 33 to 36.
3. **OD-3. Which start paths must refuse?** (ruled (a), D-3). The recon found no start-time validation, no instrumentation hook and no `next.config` hook; the only place before serving is the entrypoint's `server` verb, which `npm run dev` and a bare `next start` or `node server.js` bypass (recon § Startup and entrypoint, risks 1). Options: **(a) all three refuse, and a request-time backstop makes the flag count as off whenever `SITE_URL` is not loopback, so a path the refusal missed still shows nothing (recommended).** Whether one start-time hook covers all three, or the refusal is split (entrypoint plus the framework's hook), is the design pass's first question, and ACs 33 to 36 are the requirement either way. The backstop (AC 37) is the part that does not depend on that answer. (b) The container `server` verb only, which is the one path a deploy uses (the Dockerfile's `CMD`), and the backstop for the rest. Smaller, but `npm run dev` and `next start` with the flag and a public origin would start and show nothing marked only because of the backstop. (c) The container verb only, no backstop. Not recommended: a single guard on the one path a person does not use by hand. Moves with the ruling: ACs 34 to 37.
4. **OD-4. Fitments of a collected feed.** (ruled (a), D-5). `countedFitmentWhere` knows only feed approval, shop approval and vehicle retirement, and counts a feed's fitments whatever the state of its offers, so a `fitment` cell in a collected file would still make a public product "fit" a car (recon § Gaps). Decision 0017 already puts fitment from collected data out of scope. Options: **(a) a collected feed's fitment never counts anywhere, flag on or off; the mechanism is the design's (recommended).** Reason: 0017 says it is out; the narrowest rule that cannot leak is the one that does not depend on the flag. (b) It counts only while the flag is on. Not recommended: a second rule to test for data the decision already excludes. Moves with the ruling: AC 32.
5. **OD-5. Convergence between a collected row and a public-feed row (the question US-7.1 left to this story).** (ruled (a), D-4). Matching attaches a row to any existing product by EAN, or by brand and part number, across feeds, and a product's text is written once from the row that creates it (recon § Gaps). Today a public row that attaches to a product first created by a collected row would make that product public carrying the collected title, brand and description: collected text on a public page without the flag. Options: **(a) a product created from a marked row is itself marked; an unmarked row never attaches to a marked product and becomes its own product; a marked row may attach to an unmarked product, where it adds an offer and changes nothing the product shows (recommended).** Reason: it closes the one path by which the text leaks while keeping the local comparison the owner wants (a collected price beside a hand-written one) when the flag is on. A marked product is also public only with the flag, even if it somehow held a visible unmarked offer (AC 30), so the wall does not rest on the matcher alone. (b) A marked row never attaches to anything and a marked product never receives an offer. Simpler, but the owner loses the comparison that is the point of loading collected data to judge the prototype. Moves with the ruling: ACs 28 to 31.
6. **OD-6. Does a marked offer look different on a local page while the flag is on?** (ruled (a), D-6). Recommendation: **no (a)**. The flag exists so the owner can judge the real catalogue; a badge is a public copy change, a new string and a UX pass for a screen no visitor ever sees, and the admin product screens (S2.4) already name the feed of every offer. (b) A small marker on the product page and the offer rows. If the owner wants it, it is a later story; it is not in #306's In list. Moves with the ruling: adds an AC and a public UX pass; "no public screen changes" below becomes false.

## Story

As the owner, I load a file my local-only collector made into my local stack, behind the same two approvals as any feed, and its products and prices are visible on my local site only when I have turned on a local flag, are never indexed or counted, and cannot be shown by a site whose public address is set, so that I can judge the prototype with real prices without a collected row ever reaching a public page.

Today decision 0017 allows the collector but the app cannot tell a collected row from a hand-written one, so `CLAUDE.md` and the owner's guide forbid putting a collected file anywhere until this story ships. The only thing between collected data and a public site is the owner's care. After this story the wall is built into the data and into the start-up: a marked row is invisible to every public read unless the flag is set; the flag cannot be set on a server with a public origin; and tests fail if the wall, the ignore rules or the dependency list change.

## Acceptance criteria

Terms. A **collected feed** is a registered feed whose rows come from a file made by the owner's local-only collector (decision 0017). A **marked** offer is an offer imported from a collected feed; a **marked** product is a product created from a row of a collected feed. **The local flag** is a setting in the app's environment that is off unless it holds the value `true` (AC 11). **A loopback origin** is an origin whose host is `localhost`, an address in `127.0.0.0/8` or `::1`. **The public surfaces** are: the home category tiles and counts; the category page (cards, counts, brand chips, lowest prices, car-fit counts); the product page (its offer list, count, lowest price and structured data, and its "fits these cars" list and banner); search, including the car-filtered category and search listings; the sitemap files; `/go/<offer>`; and the 404 answer for a page that does not exist. A "refusal" in the admin is a message in Spanish next to the field at fault, a row not written or changed, and an answer that is not a server error. Copy in these ACs is intent only; wording and layout are the UX pass's. Criteria marked **[OD-n]** change with that ruling.

Registering a collected feed [OD-1]

1. On `/admin/tiendas` the admin can create a feed for an existing shop by choosing the collected-file source and giving a file name. The new feed is unapproved even when its shop is approved, is not a demo feed, has no network, and appears in the list as a collected feed.
2. A collected feed's file is read only from a second fixed folder, separate from `catalogue-files/`; no field, stored value, argument or request can name another folder, and the importer reads no collected file whose name has a directory part.
3. A catalogue-file feed cannot read the collected folder and a collected feed cannot read `catalogue-files/` or `demo/feeds`: each reports `file_not_found`, with no path, when its own folder lacks the file, even if the other folder holds a file of that name.
4. The file name of a collected feed is accepted and refused by the same rule as a catalogue file's name (US-3.7 AC 3), with the same refusals and without repeating the value.
5. A collected feed is a collected feed for as long as it exists: no form, action or crafted submission can turn a collected feed into any other source, or any other feed into a collected one; extra fields on the submission are ignored or refused.
6. Renaming the file of an approved collected feed returns it to unapproved in the same write, as for a catalogue file (US-3.7 AC 12), and the rows already imported stay marked.
7. In the feed list on `/admin/tiendas` and on `/admin/categorias`, a collected feed is identified as a collected file by its file name, not as a hand-written catalogue file, not as a shop upload and not as a network feed; it shows the same approval and paused states as any feed.
8. Registering a collected feed does not read the folder, and no page, action response, redirect, notice, log line or import report shows the folder's location or any path (US-3.7 AC 13 applies unchanged).
9. Every action this story adds or changes refuses a request with no session, a forged cookie, an expired cookie or a signed-out cookie, has no effect, and checks the role before it reads or writes anything else, including when called directly with a crafted request (guardrail 3).
10. Every such action refuses a submission from another origin and has no effect.

The marker, set by the importer [OD-1]

11. The local flag is on only when the value is exactly `true`, ignoring case and surrounding blank space; unset, empty, or any other value (`1`, `yes`, `on`, `false`) is off.
12. Importing an approved collected feed marks every offer it creates or updates, on the first import and on every re-import, and marks every product it creates; the import report is the usual line and no row text.
13. With the flag on, a marked offer is public only if its feed and shop are approved, it is not hidden, not in review and not removed, and its product is not hidden and has a mapped category; the flag lifts the exclusion of marked rows and no other rule (guardrail 1).
14. A hand-written, affiliate or demo feed's rows are never marked, and the import of those feeds, their reports and their tests behave exactly as today.

Without the flag, no public surface shows a marked row

15. On the home category tiles and counts and on the category page, a marked offer adds nothing: not a card, not a count, not a brand chip, not a lowest price, and a category whose only products are marked shows no product from it.
16. A product that is marked and has no unmarked visible offer has no public product page: its address answers exactly as an address that does not exist, and so does a car-filtered address.
17. On the product page of an unmarked product, a marked offer adds nothing: not a row in the offer list, not to the shop count, not to the lowest price and not to the structured data.
18. In search, including the car-filtered listing, a marked product is not found by its title, brand, part number or EAN, and a marked offer adds nothing to an unmarked product's result.
19. `/go/<offer>` for a marked offer answers exactly as it does for a hidden or unknown offer, and records no click.

Indexing, sitemap and clicks, flag on or off

20. A product page whose only offers come from collected or demo feeds carries `noindex` and no canonical link, flag on or off.
21. A product page carries an index signal and a canonical link only when it has at least one offer from a feed that is neither demo nor collected, in any offer state, as the demo rule works today (S6.2).
22. The category page is `noindex` with no canonical link unless its subtree holds a visible product that has an offer from a feed that is neither demo nor collected.
23. The sitemap files list no marked-only product, and no category whose only products are marked, flag on or off; a product that also has an offer from a feed that is neither demo nor collected is still listed.
24. With the flag on, `/go/<offer>` for a visible marked offer redirects to exactly the offer's address as for any offer, records no click, and still answers `X-Robots-Tag: noindex, nofollow`.
25. Demo data behaves exactly as today on every one of these surfaces.

With the flag on

26. With the flag on, every public surface shows a marked offer and a marked product that satisfy AC 13 as it shows any offer or product, with no sign that they are marked on any public screen (OD-6).
27. With the flag on, an unapproved collected feed, an unapproved shop, a hidden offer, a hidden product and an unmapped product show nothing on any public surface (AC 13 per surface).

Matching and the product's text [OD-5]

28. An unmarked row never attaches to a marked product, by EAN or by brand and part number, in either import order: it becomes its own product, and the marked product's title, brand, part number and description never appear on a public page without the flag.
29. A marked row may attach to an existing unmarked product, by EAN or by brand and part number, and the public page of that product with the flag off is the same before and after that import (AC 17).
30. A marked product is not public without the flag even if it holds an unmarked offer that is visible by any other means (for example one written to the database directly), so the wall does not depend on the matcher.
31. Two collected feeds whose rows share a valid EAN converge on one marked product, as two hand-written feeds do today.

Fitment [OD-4]

32. A `fitment` cell in a collected feed's file never makes any product or vehicle count as fitting on any surface, flag on or off; the import does not fail on it.

Refusal to start [OD-2, OD-3]

33. With the flag on and `SITE_URL` not a loopback origin (a public https origin, a public http origin, a private-network address, an unparsable value, or unset), the container's `server` verb exits with a non-zero code before it migrates, seeds or serves, and prints one fixed line that names the two settings and shows neither value.
34. The same refusal, with the same one fixed line, when the app is started with `npm run dev`.
35. The same refusal, with the same one fixed line, when the app is started with `next start` or `node server.js` outside the container's verb.
36. With the flag on and a loopback `SITE_URL`, all three start paths start the app as today; with the flag off, all three start as today whatever `SITE_URL` holds, unset or a public https origin included.
37. A backstop independent of the start path: with the flag on and `SITE_URL` not a loopback origin, the public surfaces behave as with the flag off, so a start path the refusal does not cover never shows a marked row.
38. `migrate`, `seed`, `import-feeds` and `create-admin`, and `next build`, do not refuse because of the flag, and `import-feeds` still imports and marks a collected feed.

The flag is absent by default, and the files stay out of git and the image

39. No tracked file sets the flag on: `.env.example` has no line that sets it, `npm run env:init` writes none, and `compose.yaml` passes it through with the default off; a test fails if a tracked file sets it on.
40. `.gitignore` ignores the collected folder's contents except a keep file, and `.dockerignore` excludes the folder from the build context, and the built image holds no file from it; a test fails if either entry is removed.
41. `compose.yaml` mounts the collected folder read-only into `app`, so `npm run import-feeds` and `docker compose run --rm app import-feeds` read the same file with no step beyond placing it.
42. A clean clone holds no collected file, and `npm run gate` exits 0 there, with the folder absent or empty.
43. No tracked file, fixture or test uses a real shop's name, address or product, and the story's diff holds no collected file or capture of a real page (a reviewer check).

Guards in the test suite

44. A test fails if any file under `src/` or `scripts/` imports the collector: it fails on an import of a module outside the repository tree and on an import whose module name contains "collector"; the test is shown to fail on a planted offender.
45. A test fails if the app's `package.json` dependencies, development dependencies or optional dependencies include a scraping or HTML-parsing package (those the lint ban lists) other than the Playwright test runner in development dependencies, or any dependency that points at a path, a file, a link or a git address instead of a registry version.
46. The existing scraping-library lint ban, its test, and the seams rules for `fetch`, file reads, HTTP clients, `zlib` and the XML parser still pass unchanged.
47. `tests/unit/seams.test.ts` is changed, in the same ticket as what it bounds, so that the flag is read from the environment only where the design names it, the marker and flag are named only in the modules the design names, and the one visibility rule stays the only place a marked row is excluded; each new rule is shown to fail on a planted offender.

Owner's guide and the rest unaffected

48. The owner can follow, from written steps in `CLAUDE.md` and `docs/feeds/catalogue-file.md`: that a collected file goes only in the collected folder and is registered with the collected source, never in `catalogue-files/`; that the local flag is set in his local `.env` and nowhere else; what the flag does and does not do (AC 13); that the app refuses to start with it against a public origin; that collected rows are never indexed, listed or counted; and that using collected data on a public site needs a new owner decision.
49. The guide no longer says "no collected file before S12.2", and says that the flag covers collected files only, not hand-written ones.
50. All visible text this story adds or changes comes from the es-ES message files, in the admin section kept apart from the public sections, with no inline user-facing string, and no public page, public message or `rel` attribute changes.
51. The behaviour of S2.4 (hide), S3.1, S3.7, S4.2, S6.2 and S7.1 is unchanged, and their tests keep passing without being loosened, except the deliberate changes named in ACs 44 to 47.

## Notes for the human

- **This is the guardrail 1 visibility scope.** The one shared rule in `src/server/visibility.ts` decides what every public page, the sitemap and `/go` show, and this story changes it. That is why the integration gate and a reviewer run after the build, as #306 says.
- **Where each recon gap lands.** Fitments: AC 32, OD-4. Matching across feeds: ACs 28 to 31, OD-5. `hasNonDemoOfferWhere` counting an offer in any state as "real": ACs 20 to 23; the new rule is "neither demo nor collected", still in any state, so the S2.4 decision on hidden real offers is untouched. The flag's own name and where it is read: left to the tech lead. What "public https" means: OD-2. Start paths: OD-3.
- **The flag and the indexing are two different rules, on purpose.** With the flag on, a marked product is visible on a local site and still `noindex`, still out of the sitemap, still never a counted click. The home page and the legal pages carry no per-row noindex today, so a local home page may count a marked product in a category tile; the protection for that page is the refusal and the backstop, not a noindex.
- **A file put in `catalogue-files/` by mistake cannot be detected.** Under OD-1 (a) the place decides the marker, so a collected file copied into the hand-written folder and registered as a catalogue file would import unmarked and, with both approvals, be public. The decision, the guide and S3.7's own text already forbid it; this story makes the right way the easy way and the wrong way visible in the guide, and nothing in the app can prove which kind of file a file is. (c) of OD-1 is the hardening that would.
- **The owner's local database.** A restored dump of a database that holds marked rows carries third-party data to wherever it is restored, which is why visibility is gated by the flag and not only by where the collector runs (`02-product.md` § C, residual risks). The backstop and the refusal cover the app; they do not cover a dump copied elsewhere.
- **Hand-written files are not covered.** The flag covers collected rows only; a hand-written real catalogue on a careless deploy is still the owner's care and the Before-going-live list in `mvp.md` (US-3.7 Notes for the human).
- **Issue #306 was read as relayed into the run**, not from GitHub. The ACs that go beyond its In list are the matching rule (28 to 31), the fitment rule (32), the marked-product backstop (30), the request-time backstop (37) and the guide (48, 49), each because the recon found a path by which a marked row would otherwise reach a public page.
